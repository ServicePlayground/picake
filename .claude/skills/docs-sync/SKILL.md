# 변경 후 문서 동기화

기능 개발/수정, 버그 수정처럼 코드베이스의 동작이나 구조를 바꾸는 작업을 마쳤을 때, 마지막 단계로 관련 문서를 최신 상태로 맞추기 위한 절차입니다.

## 0. 스킵 조건

아래에 해당하면 이 skill을 실행하지 않고 조용히 넘어갑니다.

- 오탈자, 포맷팅, 주석, 테스트 코드, 내부 리팩토링 등 사용자 관점에서 동작·구조·사용법이 바뀌지 않은 변경
- 이미 이번 턴 안에서 관련 문서까지 함께 수정을 마친 경우

## 1. 이번 작업에서 무엇이 바뀌었는지 파악

`git status`, `git diff`로 이번 작업에서 실제로 변경된 파일을 확인합니다. 어느 앱(`backend`/`web-user`/`web-seller`/`web-admin`)의 어느 기능/모듈이 바뀌었는지 정리합니다.

## 2. 관련 문서 탐색

대상 범위는 루트 `README.md`와 `docs/` 폴더 전체입니다. 변경된 앱/기능/모듈 이름, API 경로, 설정 값 등을 키워드로 `docs/` 하위를 검색해서 관련 문서를 찾습니다.

- `docs/common/feature/`: 기능 단위 가이드 (인증, 스토어 등록 등)
- `docs/backend/`, `docs/web-user/`, `docs/web-seller/`: 앱별 README·기술 스택 가이드
- `docs/common/structure/`, `docs/infra/`: 프로젝트 구조·인프라·배포 가이드
- 파일명에 `(구버전)`/`(이전버전)`처럼 특정 시점의 버전이 명시된 문서는 그 시점 상태를 의도적으로 보존하는 기록입니다. 현재 코드 기준으로 "최신화"하지 말고, 검색 대상에서는 제외하지 않되 원칙적으로 손대지 않습니다.

## 3. 관련 문서 수정

관련 문서를 찾았으면 사용자에게 다시 확인받지 않고 바로 수정합니다. 관련 문서가 여러 개여도 마찬가지입니다.

- 완전히 새로운 주요 기능이라 대응하는 문서가 아예 없는 경우, `docs/common/feature/` 등 가장 적절한 위치에 새 문서를 만들고 루트 `README.md`의 "📚 상세 문서" 목차에도 링크를 추가하는 것을 고려합니다. 단, 사소한 변경까지 새 문서를 만들 필요는 없습니다.
- 관련 문서가 없으면 문서를 새로 만들지 않고 그대로 넘어갑니다.

## 4. 작성 원칙

- **민감 정보 금지**: API 키, 토큰, 비밀번호, 시크릿, 내부 IP/호스트, 실제 사용자 데이터 등은 어떤 경우에도 문서에 남기지 않습니다.
- **핵심 요약만**: 세부 구현이나 사소한 내용까지 다 담을 필요 없습니다. 중요하지 않다고 판단되면 아예 언급하지 않아도 됩니다. 주요 변경 사항과 그 요약 정도만 반영합니다.
- 기존 문서의 언어(한국어)와 톤, 파일명 규칙(`... - 가이드.md`), 표/코드블록 스타일을 그대로 따릅니다.

## 5. 마무리 보고

어떤 문서를 왜 수정했는지 짧게 요약해서 알려줍니다. 관련 문서가 없어서 아무것도 수정하지 않았다면 이 단계는 생략해도 됩니다.
